# Invoice Self-Service And Management Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在 `feature/invoice` 分支修复支付设置页崩溃，并实现用户自助申请发票、管理员上传 PDF 发送邮件及全流程状态管理。

**Architecture:** 以成功充值订单 `TopUp` 作为可开票金额来源，新增发票抬头、发票申请及申请订单关联三个领域实体。订单增加 `unissued -> issuing -> issued` 状态，同时维护旧的 `invoice_issued` 布尔字段；用户申请在一个事务内锁定并占用订单，管理员发票发送采用带租约的两阶段流程，只有 SMTP 成功完成消息提交后才把申请和订单标记为 `issued`。

**Tech Stack:** Go 1.22+/Gin/GORM、SQLite/MySQL 5.7.8+/PostgreSQL 9.6+、现有 SMTP 配置、React 19/TypeScript/TanStack Router/React Query/React Hook Form/Zod、Bun、Vitest/React Testing Library、Playwright 或浏览器手工验收。

## 已有工作区现状

当前分支已是 `feature/invoice`，基于 `develop`。工作区已有未提交的初步实现，包括模型、路由、用户/管理员页面、SMTP 附件发送和 `Textarea` 导入修复。本方案是执行前的目标设计；执行时必须逐项复核已有代码，保留正确部分并修正与本方案不符的地方，不回滚用户已有的无关修改。

现有实现中已知需要在执行阶段修正的点：

- `service.SetInvoiceApplicationFailure` 当前会把申请和订单退回 `unissued`；应改为保留 `issuing`、清空发送租约并写入 `last_error`，让管理员重试而不是让用户重复申请。
- `BeginInvoiceApplicationIssuance` 当前允许部分非 `issuing` 状态直接重新进入发送；应只允许新申请或失败后释放租约的 `issuing` 申请，并用租约防止并发重复发送。
- `model.ListInvoiceOrders` 对旧行 `invoice_status` 为空的兼容不能只依赖迁移；查询和序列化边界都要把 `invoice_issued=true` 映射为 `issued`，其余旧成功订单映射为 `unissued`。
- 邮件附件文件名不得直接拼入 MIME 头；必须清理 `CR/LF`、引号和路径片段，并用 `mime.FormatMediaType` 或等效安全编码。
- 当前前端文件是 `web/src/features/invoices/*.tsx` 平铺结构，路由是 `/invoices` 和 `/invoice-management`；方案沿用这一现有结构，不创建不存在的 `admin/invoices` 路径。

## 状态与不变量

| 对象 | 状态 | 允许的转换 | 说明 |
|---|---|---|---|
| `TopUp` | `unissued` | 用户申请后变 `issuing`；兼容旧管理员接口可变为 `issued` | 仅 `status=success` 的订单可被用户选择 |
| `TopUp` | `issuing` | SMTP 成功后变 `issued` | 已被某个申请占用，用户不能再次选择 |
| `TopUp` | `issued` | 不允许用户或普通管理员回退 | 旧布尔字段必须为 `true` |
| `InvoiceApplication` | `issuing` | SMTP 成功后变 `issued`；SMTP 失败仍为 `issuing` 并记录 `last_error` | 失败申请由管理员重试 |
| `InvoiceApplication` | `issued` | 不允许再次发送 | 重复请求返回 HTTP 409 |

发送租约字段 `sending_at` 记录当前发送尝试开始时间。活跃租约期间的并发发送返回 409；租约超过 10 分钟后视为进程异常退出，管理员可重新取得租约。SMTP 失败时释放租约但保留 `issuing` 状态。这样既避免正常并发双发，也不让一次进程崩溃永久卡死申请；进程在 SMTP 已接受邮件后、数据库最终提交前崩溃时，重试可能产生一次重复邮件，这是 SMTP 外部系统无法提供 exactly-once 的已知边界，必须在管理端显示发送时间/错误并记录日志。

金额总额始终从事务中锁定的订单 `Money` 计算，前端显示总额仅作预览；后端不接受客户端传入金额。所有跨表状态变更使用 `lockForUpdate(tx)`，不使用 `gorm:query_option`。

## API 合约

现有认证和返回包装沿用项目 `common.ApiSuccess`/`common.ApiError` 风格。分页参数使用项目 `PageInfo`（`p`、`page_size`），后端限制单页不超过 100 条。

### 用户接口（`/api/user` + `UserAuth`）

- `GET /invoice/titles` -> `{items: InvoiceTitle[]}`
- `POST /invoice/titles`，JSON `{name,tax_number,address,email}`
- `PUT /invoice/titles/:id`，同上；`DELETE /invoice/titles/:id`
- `GET /invoice/orders?status=unissued|issuing|issued|all`：只返回当前用户且充值 `status=success` 的订单；默认 `unissued`；旧空状态按布尔兼容规则映射。
- `GET /invoice/applications?status=issuing|issued|all`：只返回当前用户申请。
- `GET /invoice/applications/:id`：只允许当前用户查看详情。
- `POST /invoice/applications`，JSON `{title_id,topup_ids:[number]}`：拒绝空数组、重复 ID、非本人订单、非成功订单、非 `unissued` 订单和不存在抬头；事务内创建标题/邮件快照、关联订单、数据库计算 `total_money`，并把订单改为 `issuing`。

抬头字段全部 `TrimSpace`，邮箱规范化并使用项目已有邮箱校验；错误不得泄露 SQL 或其他用户存在性。

### 管理员接口（`/api/user` + `AdminAuth`）

- `GET /invoice?status=unissued|issuing|issued|all&user_id=&keyword=`：查询全部申请，`keyword` 至少支持申请 ID、交易号和收件邮箱。
- `GET /invoice/:id`：返回标题快照、收件人、金额、订单快照、状态、错误、时间、PDF 元数据。
- `GET /invoice/template`：返回当前邮件主题和正文模板。
- `PUT /invoice/template`，JSON `{subject,body}`：主题 1-500 字符、正文 1-20,000 字符；仅保存模板文本，不执行任意代码。
- `POST /invoice/:id/issue`：multipart 字段 `file`，仅接受真实 PDF，大小 `1..10 MiB`；管理员只能对 `issuing` 且无活跃发送租约的申请发送。

模板只支持固定占位符 `{{system_name}}`、`{{invoice_id}}`、`{{recipient_email}}`、`{{title_name}}`、`{{total_money}}`、`{{orders}}`。订单号、抬头和邮箱等动态值先 HTML 转义，再做字面量替换，禁止 Go 模板函数、脚本或表达式执行。申请创建时保存标题和主题/正文快照，后续编辑抬头或模板不改变已创建申请。

## 需要确认的产品决策

本方案建议“SMTP 失败保持 `issuing`，仅管理员重试”，因为用户申请已经占用了订单，失败后退回 `unissued` 会允许用户再次申请并产生重复申请。SMTP 的“发送成功”定义为 SMTP 服务器成功接受完整 MIME 消息；这不能证明最终投递到收件箱，但已满足现有 SMTP 能力下“发送成功后再改已开具”的要求。请确认这两个决策后再开始执行任务。
